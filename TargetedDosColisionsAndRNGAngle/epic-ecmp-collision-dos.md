## 1. Why this epic exists

Equal-Cost Multi-Path (ECMP) routing decides which of several parallel links a flow takes by hashing
the packet 5-tuple plus a **salt**. ECMP is the default path-selection mechanism in almost every serious
network of the last fifteen years: data-centre leaf-spine fabrics, ISP backbones, SD-WAN, Kubernetes CNI
plugins, 5G core. If the salt is generated by a weak PRNG with a guessable or reconstructable seed, an
attacker who knows or recovers the salt can craft 5-tuples that **all hash to one egress link**. That link
saturates; any victim sharing it loses throughput; the rest of the fabric looks healthy. Swapping the salt
to a CSPRNG or QRNG makes the collision set uncomputable and the attack fails.

The plain version of that finding — "predictable salt is bad" — is true but not novel enough to carry a
paper (the source docs score it 72/100). This epic builds the **stronger claim**: the collision attacker
is not merely "precise instead of volumetric," it is **structurally invisible to the two defences that
define current DoS practice — rate limiting and throttling.** Rate limiting fails because no single source
sends enough traffic to trip a bandwidth cap; damage is done by *placement*, not *quantity*. Throttling
fails because the attacker deliberately varies its 5-tuples across many valid-looking flows, so there is no
anomalous source or flow to drop. The attacker occupies the **gap between rate limiting and throttling**.
The defence, **salt rotation**, does not act on traffic behaviour at all — it changes the hash mapping the
attacker's pre-computed collisions depend on, invalidating their work at the mechanism level with no
false positives and no detection latency.

The user-visible outcomes of this epic are three artefacts that make that argument: (1) a simulated
Mininet/OVS/Ryu testbed that runs **five experiments** proving the attacker evades both defences and that
salt rotation defeats it; (2) **two key graphs** — attacker-success-vs-source and the rotation-frequency
threshold curve; and (3) a **three-scene web demonstration** that makes the whole logical argument visible
before a reviewer reads a word of the paper. QRNG enters via the existing **Q-EaaS `GET /v1/random/bytes`**
service as one of three interchangeable salt sources — used for auditable entropy **provenance**, not to
claim superiority over CSPRNG (see §3.2).

## 3. Cross-cutting decisions

Decisions that span multiple plans and must be made once. Every `/plan-feature` invocation must respect these.

### 3.1 The attack framing is locked — this is an *attack paper*, not a *quantum paper*

The narrative every plan serves: **a new attacker class that occupies the gap between rate limiting and
throttling, defeated by a mechanism-level defence (salt rotation) with a quantified rotation-frequency
specification.** CSPRNG alone defeats the attack; that is stated, not hidden. Consequences that bind all plans:

- The attacker (P3) must be *demonstrated* to evade rate-limit + throttle (P4) that *provably stop a
  volumetric flood* — Experiments 1–3. "New attacker" is an empirical claim, never a description.
- The defence (P2 rotation) is presented as operating on the **hash function**, categorically different from
  the **traffic-behaviour** defences it does not replace but renders unnecessary.
- The write-up (P7) and demo (P6) both lead with this positioning.

> **Novelty caveat (from the §10 prior-art scan):** the source-detection-immunity *property* is not new — Crossfire,
> Coremelt, and low-rate DDoS established it. What is new here is the **first ECMP-specific articulation** of it
> (single attacker + deterministic hash placement + one link, **no botnet**) plus the rotation-cadence defence and
> the QRNG null result. Claim the instantiation, cite the property's origin — never imply the property itself is new.

### 3.2 QRNG-EaaS: the practical role, and the honest null result

The user asked to foreground **QRNG as a practical use** and to wire in the existing Q-EaaS service. Both are
done — without breaking the scientific honesty the source docs insist on. Hold two things at once:

- **The honest null result (stated everywhere):** in *this attack's threat model*, QRNG buys nothing over a
  CSPRNG — the attack fails identically under both. Experiment 4 measures this on purpose. Honest null results
  are well regarded in measurement papers and pre-empt "why quantum here?".
- **The genuine practical use (the product angle the user wants):** Q-EaaS is a *real, callable service*, and
  its developer endpoint returns **auditable entropy provenance** — a `request_id`, an `entropy_epoch` (DRBG
  reseed counter), a UTC `timestamp`, and an **Ed25519-signed `receipt`** per issuance. So the practical value
  QRNG-as-a-Service adds is **attestable, provably-sourced salt entropy**: in a compliance- or audit-sensitive
  fabric (finance, government, multi-tenant cloud with attestation requirements), an operator can *prove* the
  rotation salt came from a specific quantum entropy source at a specific epoch. That is a real differentiator
  even when the attack outcome is identical to CSPRNG. QRNG is also the **calibration ceiling** — the reference
  for "provably non-reconstructable by any means" that anchors the rotation-frequency spec's upper bound.

The framing rule so this never reads as motivated reasoning: **QRNG's practical claims are provenance,
attestation, and product demonstration — never "it stops the attack better."** The demo (P6, Scene 3) shows the
live Q-EaaS receipt/epoch/timestamp as concrete provenance; the paper (P7) states the null result plainly.

### 3.3 Visualization is a first-class deliverable, not an afterthought

The user's primary emphasis. Two visual surfaces, and they must agree with the code:

- **The web demo (P6)** is *the paper's argument made visual* — three scenes that a reviewer understands before
  reading. Built in two tiers: **Tier A** browser-only (ships immediately, GitHub Pages, conference QR code),
  **Tier B** live WebSocket to real OVS port-stat counters.
- **The two paper graphs (P5)**: attacker-success × salt-source × knowledge-level, and the rotation-frequency
  threshold curve.

Cross-cutting constraint: the **JS hash/salt/bucket logic in the demo must be identical to the Python** used in
the testbed, guaranteed by **shared test vectors** (P2 owns them). If they drift, the demo silently lies. CI/asserts
must fail on drift.

### 3.4 Simulated topology is sufficient — with one honest scale caveat

All five experiments are **mechanism, not scale** questions (does the attack evade the defences? does rotation
defeat it? what is the frequency threshold?). None need 10G silicon. The mechanism — hash, salt, bucket selection,
rate-limit/throttle flow rules — is identical in Mininet/OVS emulation. The caveat, stated honestly in P7: absolute
time-to-saturation is lower on real 10G hardware; but the **findings are scale-invariant ratios** (precision vs
volumetric, weak-PRNG vs rotating-CSPRNG). One optional hardware confirmation run pre-empts the scale critique.

### 3.5 One hash core, three salt sources, one rotation knob — decided once in P2

To stop later plans reinventing it: a single `link = hash(5tuple, salt) mod N` implementation is shared by the
controller **and** the attacker (P3 imports it — the attacker uses the real hash, not a copy). `salt_source(kind)`
yields `prng | csprng | qrng`. Rotation is a controller knob with a configurable interval (minutes → sub-second),
reinstalling group rules atomically and logging every rotation event + new salt. These signatures are frozen in P2
and consumed unchanged by P3, P4, P5, P6.

## 5. The mechanism under test — salt & rotation state

There is no application "status workflow" here; the state machine that matters is the **salt lifecycle** the
defence manipulates:

```
  salt_source(kind) ── mints ──► active_salt ──┐
                                               │  installed into ECMP group rules by Ryu
   rotation timer (interval) ── fires ─────────┤
                                               ▼
                         new_salt minted, group rules reinstalled ATOMICALLY,
                         event logged {ts, old, new, interval}
                                               │
   attacker's pre-computed collision set (valid under old_salt) ──► now disperses (invalidated)
```

Correctness invariant every plan must preserve: **rotation is a no-op for legitimate traffic** — flows just
redistribute fairly (Jain's index stays high). Rotation has cost *only* to an attacker mid-attack. Experiment 4
proves the no-cost-when-no-attack property explicitly.

Open sub-decision (see §8): rotation unit — per-flow, per-epoch, or per-time-interval.

## 6. Threat-model scope & deployment scenarios

The paper's **primary scenario is the multi-tenant cloud fabric**: attacker VM and victim VM share a physical
fabric; the attacker needs no controller access; if the ECMP salt is predictable, the attacker routes its flows
onto the specific spine link carrying the victim's traffic. Chosen because ECMP is most pervasive there, the
salt-predictability assumption is most defensible, the victim has zero fabric visibility, and a surgical low-volume
attack has the most asymmetric attacker value. Secondary scenarios named for the write-up's relevance section:
microservices east-west traffic, SD-WAN branch appliances (weaker embedded PRNGs), 5G core UPF-to-UPF paths.

ECMP-specific property that connects the "new place" to the "new solution" (closing Gap 2 in the reference doc):
in SDN the salt is **controller-managed**, so a single compromised/misconfigured controller propagates a weak salt
to the **entire fabric at once** — a single point of failure absent from per-device software hash maps. Salt
rotation at the controller is therefore a fabric-wide fix. Whether this changes the solution space *enough to
measure* is an open question (§8).

## 8. Open questions (epic-wide)

Carried from the source docs. Each has **context** (why it matters), **options**, and a **recommendation** — the
recommendation is a default to accept or override, not a decision already made. Resolve before/while running the
named plan; once answered, fold the answer into the relevant section/plan and tick the box.

### Q1 (P1/P5/P7) — Is the controller-managed-salt single point of failure *measured*, or qualitative only?
- **Context:** this is the property that connects the "new place" (SDN/ECMP) to the "new solution" (rotation) and
  closes Gap 2 from `ecmp-research-reference.md` — the original was dinged for a *generic* fix (CSPRNG helps
  HashDoS too). In a per-device hash map each device salts independently; in SDN one controller pushes one salt
  **fabric-wide**, so a single weak/compromised controller weakens every link at once — and one rotation repairs
  every link at once. That blast-radius symmetry is the ECMP-specific hook.
- **Options:** (a) **qualitative** — argue it in P7, no new experiment; (b) **measured** — add a multi-switch,
  multi-victim run showing N victims degrade simultaneously under one weak salt, and a single rotation restores all
  N together (vs isolated per-device degradation). Needs a bigger topology than the single-switch P1 baseline.
- **Recommendation:** qualitative in v1, but **design P1's topology so a second victim on a different link is cheap
  to add**, so the blast-radius measurement is a low-cost bolt-on if a reviewer pushes. Keeps the testbed small
  without painting us into a corner. *Affects P1 (topology headroom), P5 (optional extra run), P7 (framing).*
- [x] **Decision (2026-07-24):** ACCEPT rec. Qualitative in v1; P1 topology must leave room for a cheap second
  victim on a different link so the blast-radius run is a low-cost bolt-on later.

### Q2 (P2/P5) — Rotation unit: per-flow, per-epoch, or per-time-interval?
- **Context:** rotation is *the* tunable defence, and the unit defines what the Experiment 5 x-axis even means
  ("rotate faster than N seconds" only makes sense for a time interval).
- **Options:**
  - **per-time-interval** (rotate every T, traffic-independent): cleanest mapping to the practitioner spec and the
    Exp 5 curve; but rotating mid-flow reshuffles in-flight legitimate flows across links → possible packet
    reordering / latency for long-lived connections. Must check ECMP flow-affinity is preserved.
  - **per-epoch** (rotate on a logical boundary — every K packets / a controller epoch): decouples from wall-clock;
    harder to state as a frequency.
  - **per-flow** (new salt per new flow): strongest isolation, but the "rotation frequency" axis becomes
    ill-defined and the collision-set concept changes shape.
- **Recommendation:** **per-time-interval as primary** — it is what makes Exp 5's specification meaningful — and
  **measure legitimate-flow reordering cost as a secondary metric** inside Exp 4's "cost-free when no attack" check,
  so the reordering trade-off is quantified, not hand-waved. Flag the flow-affinity concern for P2's implementation.
  *Affects P2 (rotation impl + atomicity), P5 (Exp 5 axis, Exp 4 secondary metric).*
- [x] **Decision (2026-07-24):** ACCEPT rec. Rotation unit = **per-time-interval** (primary). Measure
  legitimate-flow reordering cost as an Exp 4 secondary metric; P2 preserves flow-affinity where it can.

### Q3 (P3/P5) — Full vs partial knowledge: separate conditions or collapse?
- **Context:** three levels — **full** (salt known: unrealistically strong, upper bound), **partial** (algorithm
  known, brute-force the seed: the realistic attacker), **blind** (nothing: failure baseline). Exp 5 uses partial;
  Graph 1 is source × knowledge. Full and partial produce the *same* attack once the salt is recovered — the only
  difference is reconstruction time, which is exactly what Exp 5 measures.
- **Options:** (a) **keep all three** — Graph 1 becomes a fuller 3×3 and shows the effort gradient, at the cost of
  some redundant cells (full-success ≡ partial-success given enough time); (b) **collapse full+partial** — simpler
  graph, but loses the "how much does knowledge cost the attacker" story.
- **Recommendation:** **keep full and partial distinct** — they answer different questions: full = "if the salt ever
  leaks, damage is immediate," partial = "a realistic attacker pays a reconstruction cost (→ Exp 5)." Keep **blind**
  as the failure baseline. In P7, state plainly that full is the upper bound and partial+Exp5 is the realistic case,
  so the 3×3 does not read as padding. *Affects P3 (implement all three), P5 (matrix width).*
- [x] **Decision (2026-07-24):** ACCEPT rec. Keep full, partial, blind as **separate** conditions; P7 states full
  = upper bound, partial+Exp5 = realistic case, blind = failure baseline.

### Q4 (P5/P6) — Tier B replay dataset: all 3×3 or a subset?
- **Context:** Tier B replay plays recorded runs so a conference demo needs no live infra. Full grid = 3 sources ×
  3 knowledge = 9 runs, plus the rotation-interval sweep for the Exp 5 slider. Most cells never appear on screen.
- **Options:** (a) **full 3×3 + sweep** — can answer any off-script question live, but most recordings are unused;
  (b) **subset the three scenes actually need** — Scene 1 (volumetric + defences), Scene 2 (precision + weak-PRNG),
  Scene 3 (precision + CSPRNG-rotation + the full interval sweep the slider drives) + one **QRNG run** for the
  provenance display.
- **Recommendation:** **record the subset** (three-scene runs + QRNG provenance run + the complete rotation-interval
  sweep the slider needs), and skip redundant cells such as *blind* — a failed attack looks like Scene 1's healthy
  state, which the demo already shows. Note the skipped conditions in the demo README so "subset" is not mistaken
  for "all conditions covered." *Affects P5 (what to record), P6 (Tier B replay scope).*
- [x] **Decision (2026-07-24):** ACCEPT rec. Record the **subset** (three-scene runs + QRNG provenance run + full
  rotation-interval sweep); skip blind; note skipped conditions in the demo README.

### Q5 (P1/P7) — Related-work section: before or after the experiments?
- **Context:** the paper positions against HashDoS, algorithmic-complexity attacks, and ECMP load-balancing
  literature. The "novel contribution" claim (an attacker in the gap between rate-limiting and throttling) depends
  on no prior paper already occupying that exact gap.
- **Options:** (a) **before** — de-risks "someone already did this" before building the testbed, and could reveal

- **Recommendation:** **split it** — a *lightweight related-work scan before P1* purely to confirm the novelty claim
  holds (cheap insurance; if a prior ECMP-collision-DoS paper exists, the whole framing must adjust *now*, not after

- [x] **Decision (2026-07-24):** RESOLVED — the pre-build scan **has been run** and is recorded in **§10**. Verdict:
  publishable-novel **with careful positioning**; the raw attack pattern and the keyed-hash defence are *not*

  *full* related-work section is still written after P5 (per rec); §10 is the pre-build novelty anchor.

### Q6 (P2/P5/P6 setup) — Which Q-EaaS deployment, and who mints the key?
- **Context:** the `qrng` salt source needs a base URL + an API key; minting a key needs an `ADMIN_TOKEN` holder

- **Recommendation:** **use hosted `api.qeaas.eu` for the P6 demo / provenance shots** (that is the real-product
  story the user wants surfaced) and **local for the P5 Experiment 4/5 sweeps** (where a run must not die mid-sweep

  config per context), P5, P6.*
- [x] **Decision (2026-07-24):** RESOLVED — **the project owner is the admin and holds `ADMIN_TOKEN`; owner mints

### P2 — Salt engine: PRNG/CSPRNG/QRNG sources, rotation, JS↔Python parity (source EPIC 1)

  - Rotation is a no-op for correctness — legitimate flows just redistribute fairly.
  - Shared test vectors: identical `(5tuple, salt) → link` in Python and JS. CI/asserts fail if they drift.
  - **Done when:** all three sources feed the same hash; rotation reinstalls a fresh mapping live; JS and Python agree on every vector.
- **Depends on:** P1 (topology + confirmed hash path).
- **Focus notes:** the `qrng` source calls `GET /v1/random/bytes?size=32&format=hex` with header `X-API-Key: <key>` and records the returned provenance (`request_id`, `entropy_epoch`, `timestamp`, `receipt`) — this is the concrete "QRNG practical use" (§3.2). No Python client for this endpoint exists in the repo yet; write a thin one. Handle `503 low_quantum_entropy` (entropy gate) and `429` (quota/rate) gracefully — fall back or retry, never crash the controller.
- **Conventions to follow:** mirror the Q-EaaS README curl examples; `secrets.token_bytes` for CSPRNG; `random` with a fixed/known seed for the weak PRNG.
- **Out of scope:** consuming the sources in experiments (P5); the visual provenance display (P6).

## 10. Related work & positioning (novelty scan, 2026-07-24)

A prior-art scan was run before build (§8 Q5). **Verdict: publishable-novel as the first ECMP/fabric-layer
salt-collision link-flood with a rotation-cadence defence and a QRNG calibration ceiling — but only with careful
positioning. It is NOT free to claim it invented single-bucket hash-flooding or keyed-hash defence.** Novelty splits
three ways:

- **The attack** (ECMP salt-collision melts one egress link): free at the routing layer — no dedicated paper — but
  the *pattern* (predictable hash → flood one bucket) is documented for NIC RX-queues (RSS secret key) and blockchain
  shards ("single-shard flooding"). Novelty = the ECMP/multi-hop-fabric **instantiation + analysis**, not the raw idea.
- **The defence** (salt rotation, CSPRNG/QRNG): the principle (keyed hash defeats collisions) is settled (SipHash,
  RSS secret key, Redis per-exec seed). Fresh parts: line-rate ECMP egress application, the **rotation-cadence vs
  salt-reconstruction-time** timing analysis, and the **QRNG-as-calibration-ceiling null result**.
- **The "invisible to rate-limiting AND throttling" framing**: novel as *articulation*, known as *property*.
  Source-diverse, individually-legitimate traffic that evades per-source detection is the defining feature of
  Crossfire, Coremelt, and low-rate DDoS. Claim the sharper ECMP-specific articulation; cite the property's origin.

### Must-cite-and-distinguish (the reviewer-killers)
| Work | Why close | How we differ |
|------|-----------|---------------|
| **RSS secret key** (MS NDIS docs; Linux `scaling.txt`) | Exact attack+defence shape one layer down — random per-boot hash key so no one can craft packets onto a single RX queue | Multi-hop fabric with per-switch seeds; salt reconstructed by active cross-fabric probing; line-rate rekeying has different cost/consistency constraints; blast radius = shared multi-tenant link, not one host's queue |
| **Nguyen & Thai, "single-shard flooding"** (arXiv 2007.08600 / IEEE TDSC 2022) | Same name-idea: hash picks the shard → attacker floods one shard | Network data-plane vs blockchain consensus; defence = rotation of a keyed hash vs their TEE; attacker reconstructs a salt vs exploits a public deterministic hash |
| **Crossfire** (IEEE S&P 2013) / **Coremelt** (ESORICS 2009) | Same threat model: target-link DoS with legitimate-indistinguishable flows evading source detection | **Single attacker + deterministic hash placement + exactly one link, no botnet**; placement is *chosen*, not *statistical* |

## Appendix A — QRNG-EaaS connection & key-mint runbook

The user's explicit ask: document how to connect to the existing QRNG service and **mint an API key**. These are
the concrete setup steps for the `qrng` salt source in **P2**. Facts verified against `qrng-eaas/api/`.

### A.1 Endpoint used by the salt source

```
GET /v1/random/bytes?size=<32..4096>&format=<hex|base64>
Header: X-API-Key: <plaintext key>
```
- `size` is required, min **32** bytes (plenty for a salt — request `size=32`). `format` defaults to `hex`.
- JSON response with provenance:
  ```jsonc
  { "request_id": "...", "format": "hex", "data": "<hex salt bytes>",
    "entropy_epoch": 3, "timestamp": "2026-...Z", "receipt": "qeaas1.<payload>.<sig>" }
  ```
- `receipt` is an Ed25519-signed token; `entropy_epoch` is the DRBG reseed counter. These four fields are the
  "provenance" the demo (P6 Scene 3) and paper (P7) display.
- Failure modes to handle in the client: `401 missing_api_key` / `401 invalid_api_key` (auth), `429` with
  `Retry-After` (quota/rate), `503 low_quantum_entropy` (entropy gate — pool degraded).
- Anonymous fallback (no key, no provenance, base64, max 64 B): `GET /random?bytes=<1..64>`. Use only for a
  smoke test; the provenance story needs the keyed endpoint.

### A.2 Mint an API key — two equivalent ways (needs `ADMIN_TOKEN`)

There is **no public signup**. A key must be minted by whoever holds the admin token (see §8 Q6).

**Way A — local CLI** (run from `qrng-eaas/api/`):
```
python -m scripts.mint_key --owner ecmp-dos-testbed --tier default
# prints once: api key for 'ecmp-dos-testbed' (tier=default): <KEY>
```

**Way B — admin HTTP route:**
```
curl -s -X POST "$API/admin/keys" \
  -H "X-Admin-Token: $ADMIN_TOKEN" \
  -H 'content-type: application/json' \
  -d '{"owner":"ecmp-dos-testbed","tier":"default"}'
# returns {"api_key":"<KEY>", ...} once — store it; only the hash is kept server-side
```
Key format: `secrets.token_urlsafe(32)` (~43 chars). Only its HMAC-SHA256 hash is stored, so **copy it on
first display** — it is not retrievable later. Revoke via `python -m scripts.revoke_key ...` or
`POST /admin/keys/revoke`.

Tiers / quotas: `default` = 256 KB/day, 120 req/min; `iot` = 10 MB/day, 600 req/min; `trusted` = 500 MB/day,
1,200 req/min. `default` is ample — a 32-byte salt every few seconds is well under 256 KB/day.

### A.3 Where to point it — base URL

- **Local:** `http://localhost:8000` — run from `qrng-eaas/api/`:
  `uvicorn main:app --reload --port 8000 --env-file .env` (env needs `DATABASE_URL`, `REDIS_URL`, `MASTER_KEY`,
  `ADMIN_TOKEN`, `WEB_ORIGIN`).
- **Hosted:** canonical `https://api.qeaas.eu`, or the Vercel deployment `https://quantum-research-api.vercel.app`.
- The salt source reads its base URL from config/env (decision Q6).
